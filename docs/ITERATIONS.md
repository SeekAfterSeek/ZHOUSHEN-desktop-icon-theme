# 迭代记录：11 个版本是怎么收敛的

> 这份文档按时间顺序记录每一次改版：**为什么改、改了什么、结果如何、用户怎么评价**。
> 它的价值不在最终答案，而在「错误是怎样被一个个找到并修掉的」。

---

## 起点：需求本身就很窄

用户的原话是：

> 只想换图标的外观，**不改变壁纸，不改变背景**。
> 做好灰度隔离，如果我不满意的话，可以回退到什么都没有发生过。

这两句话定死了整个项目的边界：

1. **只动 .lnk 的 IconLocation**，其他一律不碰。
2. **必须可回退**，且回退要做到「像什么都没发生」。

后面所有的技术选择，都是从这两条推出来的。

---

## v1 · 深蓝扁平 glyph

**想法**：做一套统一的深海蓝扁平图标，干净、成套。

**做法**：纯 PIL 绘制 24 个矢量风格图标，深蓝渐变底 + 白色 glyph。

**结果**：❌ 用户反馈「不怎么好看」。

**教训**：扁平 glyph 的信息量太低。这套图标像是一个设计练习，而不是「周深主题」。
一个主题如果没有人物，那它跟任何一个免费图标包没有区别。

---

## v2 · 舞台照 + 原图标轮廓

**想法**：保留 v1 的视觉框架，但把背景换成周深的舞台照，前景叠加原应用的白色轮廓。

**做法**：舞台照 → 高斯模糊 → 压暗 → 叠白色描边的原图标轮廓。

**结果**：❌ 轮廓压在脸上，人物表情被破坏。

**教训**：轮廓和照片是**竞争关系**，不是叠加关系。两者都要占据视觉中心，结果互相削弱。

---

## v3 · 写真满铺 + 右下角角标

**想法**：参考 QQ音乐的名人联名图标 —— **整张图标就是人物照片**，右下角放一个小的原应用标志作为身份标识。

**做法**：
- 照片按人脸位置裁剪成方形满铺
- 右下角一个 96px 的白色圆形角标，里面是原应用图标
- 角标带深色描边和投影，保证在任何背景上都清晰

**结果**：✅ 方向对了。这是整个项目第一个被认可的方向。

**关键收获**：**角标是这个设计的支点**。它同时解决了两个矛盾 ——
照片要满铺才有视觉冲击，但满铺之后用户认不出是哪个应用。
用一个小的白色圆形角标把「这是谁」和「这是哪个应用」分离开，两个需求就不再打架。

这个结构一直沿用到 v11，没有变过。

---

## v4 · 每个 APP 配一张配色匹配的照片

**想法**：不能 24 个都用同一个色调。每个应用的图标有自己的主色（微信绿、QQ音乐黄、B站粉），
应该给每个应用配一张**配色接近**的周深照片。

**做法**：手工浏览素材，按颜色分组，逐个人工挑选。

**结果**：⚠️ 方向对，但配色是「靠眼睛猜」的。

**问题**：24 个应用 × 大量候选 = 人工不可维护。而且「觉得像」和「客观上接近」是两件事。

---

## v5 · 异形图标 + 提亮

**想法**：方形太普通，做成拱形、鹅卵石形、波浪形，更有设计感。

**做法**：加入了 5 种蒙版形状（squircle / circle / arch / pebble / blob），
每 5 个应用循环一次形状。同时加了外发光、四角星点、底部压暗。

**结果**：⚠️ 用户提出两个问题：

1. 「蒙了一层暗沉沉的遮罩」—— 底部压暗 + 整体亮度不足
2. 形状太多太杂，反而不统一

**修法**：亮度 ×1.16、饱和度 ×1.28，去掉大面积压暗，只保留角部极轻的暗角。

**教训**：**「有设计感」和「能看清人」是对立的。** 任何装饰都不能盖住脸。

**后来的结局**：异形在 v7 之后被用户明确否决 —— 「效果图的图标形状都做成圆角方形或者圆形」。
最终只剩两种形状。这条弯路走完了才知道：**主题的个性应该来自照片和配色，不是来自形状的奇形怪状。**

---

## v7 · 按「背景色」匹配

**想法**：把配色匹配自动化。先从 `FINAL_200`（人工精选的 200 张）里算每张图的颜色分布，
再按应用图标的主色做匹配。

**做法**：64×64 缩略图 → HSV 分 11 个色段统计占比 → 与应用图标配色做加权打分 → 贪心分配。

**结果**：⚠️ 用户看对比图后说：

> 微信，我看好第一版。
> QQ音乐，我希望第三版的图片加上第一版的黄色圆边。
> B站，我喜欢第一版。

**关键问题浮现**：用户评价的是「**人**」和「**氛围**」，而算法优化的是「颜色分布」。
两者经常不一致。

---

## v8 · 改为按「衣服色」匹配

**用户的关键一句**：

> 人物……你要抓取它衣服的颜色，是主要的。

**做法**：
1. 用肤色蒙版定位人脸
2. 从下巴往下取一个矩形区域作为「衣服区」
3. **只用衣服区的颜色**参与匹配，背景色不参与

**结果**：✅ 明显更和谐。这是配色逻辑上最重要的一次转向。

**同时修了一个 bug**：衣服色的置信度算出了 280 / 2463 / 3969 这种不可能的值。
原因是分母用了「满足条件的像素数」，而不是「区域总像素数」。
改成统一分母后，置信度回到 0~1 的正常区间。

---

## v9 · 图标色 × 衣服色双约束

**想法**：既然图标色和衣服色都重要，那就两个方向同时约束。

**结果**：⚠️ 过度约束。同时满足两个方向后，可选照片急剧减少，质量下降。

**教训**：两个目标应该**加权融合**，不该**同时硬约束**。这直接导向 v11 的三标准加权。

---

## v10 · 衣服色为准 + 小脸裁剪放大

**用户反馈**：

> 衣服符合就行，脸不够大，可以截取呀。

**做法**：脸小不淘汰，改为在渲染时按人脸位置放大裁剪。

**结果**：✅ 接近可用，但仍有问题：

- 人脸位置靠肤色估算，经常把手肘、暖光背景当成脸
- 24 个应用里有近似重复的照片

---

## v11 · 三标准加权 + 调色 + 唯一性（终版）

用户给出了明确的三条标准和权重诉求：

> 1. 配色和原始图标的相似度最高
> 2. 衣服的颜色和主色最和谐
> 3. 颜色齐全

### 评分公式

```
score = 0.34 × cos(照片色彩分布, 原图标配色)
      + 0.34 × harmony(衣服区颜色, 原图标主色)
      + 0.20 × completeness(原图标主色在照片里的覆盖率)
      + 0.07 × 脸够大
      + 0.05 × 清晰度
```

### 这一版的四个关键突破

**① 新增调色层 —— 只挑照片是不够的**

审计发现：腾讯会议原图标是纯蓝色方块，选中的照片余弦相似度只有 0.23。
原因很根本 —— **真实照片的颜色分布永远不可能等于扁平 logo**。

Chrome 图标是红黄绿蓝四色，而在 4800 张素材里**一张同时具备四色的照片都找不到**。

解法是加一层调色：
- 色相旋转到图标主色相
- 饱和度按图标饱和度缩放
- 黑白倾向（图标黑/白为主时压亮度）
- 缺失色在背景极淡补光

**但这带来了新问题**：第一版调色把**头发染成了绿色和紫色**。
修法是加「人头保护椭圆」—— 以人脸框为中心放大 1.55 倍的椭圆整体跳过调色，
不只是保护皮肤。

**② 人脸检测彻底换掉**

原方案用肤色阈值检测，灾难性失败：

```
检测框宽度 fw = 1.00  ← 横跨整幅图
```

因为舞台照的手臂、暖光、木质背景都落在肤色范围内。

改用 **YuNet 深度模型**后，24 张全部检出，置信度 0.85~0.95。

**③ 材料池从 1021 张扩到 2843 张**

用户说「再找找」。于是把磁盘上**全部 5151 张源图**扫描一遍，
提取衣服色、背景色、整图色、人脸框、清晰度、构图指标，感知哈希去重后得到 2843 张。

**④ 图案重复的根因**

用户敏锐地指出「腾讯会议和之前的图标图案重复了吧」。

一查发现：**v7 里 WPS 和网易邮箱、百度网盘和 PyCharm、DSH 和剪映，各自都在用同一张照片。**

更隐蔽的是另一类：`p0_0032_1.jpg` 与池内另一张的 pHash 距离只有 **1** —— 它们不是同一张，
是同一张图的**相邻帧**。

解法是三重约束：
- 文件不重复
- pHash 汉明距离 ≥ 10
- 连拍系列（`station_20261025_76889_*` 这种）全局只用一次

### v11 的最终审计结果

| 指标 | 结果 |
|---|---|
| 你的逐条颜色指令 | **24/24 通过** |
| 形状合规（IoU） | **24/24 = 1.00** |
| 真重复（pHash < 6） | **0 对** |
| 配色覆盖均值 | 0.708 |
| 衣服和谐均值 | 0.665 |
| 颜色齐全均值 | 0.708 |
| 平均亮度 | 117（无暗沉） |

**仍未达标**：绿色是硬瓶颈。素材库里绿衣只有 11 张，WorkBuddy 和 360 的绿色
只能靠背景补光，配色覆盖分别为 0.50 和 0.31。这是素材量的问题，不是算法的问题。

## Plan B / Plan C · 方法可迁移性验证

用户的挑战：

> 用过的都不用，再给我出一版完全不一样的 Plan B 和 Plan C。要求和标准都不变。

这是一次真正的验证 —— 如果方法是对的，那么在素材受限时也应该能产出合格结果。

### 做了什么

1. **汇总历史用过的全部照片**（v3~v11 共 112 张），全部排除
2. **两套方案联合求解**，保证 B、C 之间也不重叠
3. 加上连拍系列约束

### 这轮暴露的两个新问题

**① 素材库里混着「不是周深」的人**

Plan B 的 VS Code 位出现了一位老先生，Plan C 的 WPS 位出现了穿正装的陌生人。

试了两版人脸识别方案（LBP 直方图、10 锚点投票），**都失败了** ——
那位陌生人的相似度 0.870，反而**高于中位数**。手工特征对同族面孔的区分度不够。

最终解法是**人工审核 278 张候选**，逐张肉眼过，圈出 24 张坏图：
- 非周深 8 张
- 带文字海报 8 张
- 空舞台/远景 6 张
- 拼图/背景板 2 张

**② 自动评分完全不看构图**

「全能录屏」位选了空舞台，「WPS」位选了生日蛋糕场景。
因为纯颜色指标不知道画面里是什么。

加了构图质量筛：
- 人脸高度 ≥ 画面 5.5%（排除远景小人）
- 人脸水平位置在 15%~85%（排除边角人物）
- 人脸垂直位置在 10%~62%

### 结果

| | Plan B | Plan C |
|---|---|---|
| 与历史版本重叠 | **0** | **0** |
| B 与 C 之间重叠 | **0** | **0** |
| pHash 冲突 | **0** | **0** |
| 指令通过 | 22/24 | 22/24 |
| 平均分 | 0.692 | 0.662 |

Plan B/C 的平均分低于 v11（0.726），因为可用的素材只剩 145 张构图合格的图，
且两套方案之间还要互斥。

## 复盘：这个项目最有价值的三个东西

**1. 一套可验证的配色匹配方法**

不是「看着好看就行」，而是三条标准 + 加权 + 可审计。
每一版都能算出一个分数，能对比、能回归测试。

**2. 一组反直觉的系统行为记录**

ICO 帧格式、ASCII 路径、PowerShell BOM、单元素数组退化。
这些不是文档里写着的，是撞出来的。见 [`PITFALLS.md`](PITFALLS.md)。

**3. 一个诚实的失败清单**

异形形状走错了、扁平 glyph 走错了、肤色人脸检测走错了、
按背景色匹配走错了、人工特征做人脸识别走错了。

每一次走错都留下了一个可复用的判据。
